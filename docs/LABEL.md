# Labeling Strategy

The dataset under `data/` is generated from the `rcutils` C sources with a hybrid labeling pipeline.

## Extraction

Function definitions are parsed with tree-sitter, which gives the extractor a real syntax tree instead of a line-based approximation. The function slice, function name, and AST-derived metrics all come from that parsed tree, so the datapoints stay anchored to the actual C source.

## Labeling

- `high_level_purpose` is generated by an LLM through `src/llm.py` using a strict system prompt. The prompt requires a JSON object with a single `high_level_purpose` field, and the script parses, validates, and normalizes that response before writing it out.
- `ast_features` is computed directly from the tree-sitter AST. It includes `ast_depth`, `cyclomatic_complexity`, `statement_distribution`, and `pointer_dereferences`.
- `control_flow_elements` is derived mechanically from the function body as a count map over `if`, `for`, `while`, and `return` nodes.
- `side_effects` is derived from the function body with a small, fixed rule set that looks for common I/O, memory, and system-clock APIs. If none of those identifiers appear, the list is empty.

## Why This Is Reliable Enough

The pipeline is reproducible and low-variance: the same source file, prompt, and model settings produce the same style of output, and the script validates the result before writing it. The purpose label is constrained by a narrow instruction set, checked for code-like or overly long output, and kept short, which reduces drift. The other labels are still grounded directly in lexical evidence from the code, so the overall datapoint remains interpretable and easy to sanity-check.
